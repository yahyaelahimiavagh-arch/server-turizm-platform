# STTI v0.7.0 — WordPress Review Relations

Status: implementation candidate / private-only

## Scope

v0.7.0 extends the existing private Tour Intelligence editor with a relation-review graph. It does **not** open any public Tour surface.

The release adds:

- first-class Route Variants that reference existing route stops;
- grouped Hotel Options without copying Hotel Intelligence-owned facts;
- Hotel Intelligence identity links using canonical `STH-######` stable IDs only;
- Transport Relations that may reference route stops and Route Variants;
- per-relation Human Review state (`pending`, `confirmed`, `rejected`) with server-owned reviewer/timestamp audit metadata;
- an approval gate: a candidate cannot be editorially approved while active relations are pending, structurally invalid, or unresolved.

## Truth policy

Unknown information remains unknown. The editor must never infer:

- a primary route variant;
- a hotel match from a similar name;
- a selected hotel option;
- origin/destination stop references from free-text transport labels;
- a Hotel Intelligence stable ID;
- public/indexable readiness from Human Review completion.

Legacy relation rows that have no review state are treated as `pending`, never `confirmed`. Client-supplied `reviewed_by` / `reviewed_at` values are not trusted; the WordPress save layer stamps review transitions from the authenticated reviewer and server time.

## Relation contracts

### Route Variant

A variant contains its own `variant_id`, optional source-backed label, role (`unknown`, `primary`, `alternative`), references to existing stop/hotel/transport IDs, human-review state, review note, and general note. Missing membership is not auto-filled.

### Hotel Option / Hotel Intelligence relation

Each existing hotel relation remains the stay-context record. v0.7.0 adds:

- optional `option_group_id` for alternatives;
- `selection_status`: `unknown`, `selected`, or `alternative`;
- `review_status`: `pending`, `confirmed`, or `rejected`;
- `review_note`.

`mode=hotel_intelligence` requires a canonical `STH-######` link. The relation resolver only verifies identity/existence. It does not copy hotel name, stars, gallery, coordinates, amenities, verification state, or public URL into STTI.

`mode=unresolved` is valid for a private candidate and preserves the source hotel name. It is not automatically promoted to Hotel Intelligence. Option groups may have zero selected rows (unknown is allowed), but more than one `selected` row in the same group is rejected as contradictory.

### Transport relation

Transport keeps the existing source-backed free-text `from` / `to`, provider, reference, and note. v0.7.0 adds optional `from_stop_ref`, `to_stop_ref`, `route_variant_ref`, plus Human Review state. Free text is never converted into refs automatically.

## Human Review workflow

Private drafts may contain pending or unresolved relation data. Structural errors still block save. Editorial `approved` is blocked until every active relation is human-confirmed and every Hotel Intelligence link that claims to be linked resolves to exactly one Hotel entity.

Rejected rows may remain in the private candidate as review evidence and do not block approval when unreferenced. Active Route Variants may not reference rejected hotel or transport relations, and active transport may not point at a rejected Route Variant. At most one active Route Variant may be marked `primary`; zero is valid and is not auto-filled.

## Locked surfaces

The following remain hard OFF in v0.7.0:

- Tour public routes
- Tour indexation
- Tour sitemap entries
- Tour schema output
- Tour canonical/robots output
- Tour homepage adapter
- automatic publication after review

Private admin preview behavior remains unchanged.

## Runtime gates

Before runtime acceptance:

1. PHP syntax/lint passes.
2. Existing v0.6.5 AI Completion contract tests remain green.
3. Existing valid REVIEW / tampered hash / wrong duration / indexable request / PARTIAL import tests remain NO WRITE.
4. v0.7.0 relation unit contract passes.
5. WordPress+MariaDB disposable runtime verifies relation normalization and approval gating.
6. Installable ZIP is generated by the existing package workflow.
7. No production deployment occurs from CI.

## Merge policy

One implementation branch and one PR are used when the complete candidate is ready. Merge requires explicit owner approval after final CI/runtime evidence review.
